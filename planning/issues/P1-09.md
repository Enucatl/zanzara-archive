# [P1-09] Shared GPU runtime base, Python 3.14 and model-image disk budget

- Stable ID: P1-09
- Executor: Luna
- Kind: Implementation
- Parent: P1
- Blocked by: P0, P1-H01

## Outcome and requirement

Six model candidates and the current independently built GPU images; output one repository-owned, pinned shared GPU runtime base and six thin service images. The base must target Python 3.14, provide one compatible `torch`/`torchaudio` pair and one shared Transformers installation, and keep model weights in external read-only caches. The build must have one shared heavyweight CUDA/Python/ML layer stack rather than multiplying it across services.

This issue makes the disk budget and runtime unification explicit before P1-01 accepts the six service images. The current baseline is five `pytorch/pytorch:2.7.1-cuda12.8-cudnn9-runtime` images and one `2.8.0` image, all Python 3.11.13; the baseline image sizes and build-cache usage must be measured rather than inferred from virtual image sizes.

Current upstream candidates observed on 2026-09-12 include `pytorch/pytorch:2.14.0-cuda13.0-cudnn9-runtime` and `2.14.0-cuda13.2-cudnn9-runtime`. Their published image metadata reports Python 3.12, not 3.14, and the tag listing has no Python 3.14 variant. If Python 3.14 remains required, build the repository-owned base from a pinned CUDA 13 runtime plus Python 3.14 and install the selected PyTorch/Torchaudio wheels there; do not install the upstream Python 3.12 stack and then add a second Python runtime on top without measuring the resulting duplication.

The final shared base selects CUDA 13.0 because matching CPython 3.14 `torch` and `torchaudio` wheels are available as `2.14.0+cu130` and `2.11.0+cu130`; the CUDA 13.2/PyPI Torchaudio combination failed its runtime CUDA-version check. It also uses `sentencepiece==0.2.2` so the CPython 3.14 wheel is used instead of introducing a compiler toolchain for the older `0.2.0` pin. All six adapters are re-locked and pass the required RTX 5090 GPU smoke.

## Design and interfaces

Use D1's package/deployment boundary, D5's model contracts and D11's operational profiles. Add a repository-owned shared-base Dockerfile and pinned build metadata under the service image tree. The shared base may be derived once from a pinned upstream CUDA/PyTorch runtime, but service Dockerfiles must inherit from that base and must not independently install a second CUDA/PyTorch/Transformers stack.

The target runtime is Python 3.14. Re-lock all six service environments for the target interpreter and select the newest mutually compatible stable PyTorch/Torchaudio pair that supports the RTX 5090 and all six adapters. A newer pair may be selected when required for Python 3.14; the existing 2.7.1/2.8.0 split is not a design constraint. Transformers must be installed once in the shared base at one exact version/source and consumed by services through the shared environment. If Parakeet, BGE-M3, WeSpeaker, pyannote or another required adapter proves incompatible with one version, preserve the smallest justified exception and attach reproducible evidence; do not silently retain duplication.

These are inference-only images. Use a CUDA/PyTorch `runtime` base; do not use the larger `devel` variant in the final image. A temporary build stage may use compiler tooling only if a required dependency has no compatible wheel, but compiler toolchains, `nvcc` and build caches must not be copied into the runtime base. The shared base uses `gcc` only to precompile Triton's small C driver helper, then purges the compiler; no compiler or `nvcc` remains in the final runtime. The current service sources show no custom CUDA extension or fine-tuning build requirement.

## Bounded steps

1. Measure the current baseline with `docker system df -v`, image layer digests/sizes, BuildKit cache usage and model-cache usage. Report virtual image size separately from shared layer bytes, unique image bytes and build cache bytes.
2. Implement one pinned, repository-owned GPU base containing the selected Python, CUDA/PyTorch/Torchaudio runtime, `uv`, common native/runtime packages and the one exact Transformers version/source. Do not bake model weights, Hugging Face caches, ModelScope caches, WavLM checkpoints or package-download caches into image layers.
3. Re-lock each service for the shared interpreter and runtime. Reduce each derived image to model-specific code, genuinely required non-shared dependencies and small adapter assets; use external read-only model mounts and bounded BuildKit cache mounts where useful.
4. Rebuild all six service images from the shared base and prove that the heavy base layer stack is inherited once. Remove only superseded Zanzara image/cache entries after measurements are captured; retain a safe cleanup/runbook command rather than using a broad prune.
5. Run all six real RTX 5090 GPU smokes and record output shapes, finite-value checks, model revisions, runtime versions, image/base digests, VRAM and timings. Preserve the current model contracts and preprocessing.

The first cudnn-runtime base-only experiment is reproducible with `docker build --progress=plain --file services/shared-base-experiment/Dockerfile --tag zanzara-archive/shared-base-experiment:2.14.0-cu130-py314 .`. It produced a 14.64 GB local image (`10.45 GB` unique and `4.19 GB` shared according to `docker system df -v`) with one 6.3 GB Python/ML installation layer, and the GPU smoke passed on the RTX 5090. Repeating the experiment from the digest-pinned `nvidia/cuda:13.0.2-base-ubuntu24.04` image with `UV_COMPILE_BYTECODE` disabled produced a 9.82 GB local image (`9.26 GB` unique and `562 MB` shared in the current Docker store), with a 6.02 GB Python/ML installation layer. Its GPU smoke also passed on the RTX 5090. The site-package breakdown remained approximately `nvidia 3.2 GB`, `torch 1.2 GB`, `triton 891 MB`, `scipy 83 MB`, `transformers 56 MB`, and `sklearn 32 MB`, confirming that the saving is from the raw NVIDIA base rather than removal of the PyTorch wheel CUDA payload. This is base-only evidence; it does not satisfy the six derived-image acceptance items.

## Final evidence (2026-09-12)

The reviewed shared base is `zanzara-archive/shared-base:py314-cu130` (`sha256:df7c3a4308f76785dd17d7f7ddf74e5471dcf2d1cafba679b7b1a75beceecca4`, 10.51 GB virtual image size). Its history has one 6.53 GB Python/ML installation layer and one 55.3 MB `uv` layer. The final image contains the precompiled Triton helper but no `gcc`, `g++` or `nvcc`.

All six derived images inherit that base. Docker reports these virtual/unique sizes: diarization 10.9/438 MB, text embeddings 10.7/186.9 MB, ERes2Net 10.8/190.7 MB, Parakeet 11.0/457.3 MB, WavLM 11.2/589.6 MB and ResNet293 11.1/611.1 MB. No service-specific layer exceeds 1 GB. BuildKit measured 81.89 GB total with 47.88 GB reclaimable before cleanup and 53.21 GB total with 19.2 GB reclaimable after the age-bounded cleanup; stale compiler-path experiment records were removed without pruning model caches, volumes or unrelated images.

The six GPU smokes passed on the NVIDIA GeForce RTX 5090 (driver 590.48.01, 32,607 MiB): Parakeet `[1, 55]`, diarization `[3, 3]`, ResNet293 `[256]`, ERes2Net `[192]`, WavLM `[256]` and text embeddings `[1024]`. Every probe reported Python 3.14.7, Torch 2.14.0+cu130, Torchaudio 2.11.0+cu130 and Transformers 5.17.0. Private evidence is in `.git/zanzara-evidence/P1-01/*.json`; the smoke audio for ERes2Net is a public ModelScope example, so this proves runtime compatibility rather than archive-quality accuracy.

## Inputs, outputs and failure behavior

Inputs are the six locked model artifacts, current service manifests, the RTX 5090 and the measured image/cache baseline. Outputs are the shared-base Dockerfile and lock/build metadata, six thin derived images, a before/after disk report and updated runtime/model evidence. Preserve source/model/configuration provenance and fail without publishing partial artifacts when validation fails.

Any Python 3.14, CUDA, Torch/Torchaudio, Transformers or adapter incompatibility is a review blocker until narrowed to a reproducible package/version constraint. A second heavyweight base lineage, per-service duplicate Torch/CUDA/Transformers installation, model weights in image layers, unmeasured disk growth or a failed real GPU smoke blocks completion.

## Exclusions

No model substitution, quality benchmark, application inference integration, shared long-lived process that mixes model contracts, deletion of the approved model caches, or broad Docker pruning. Do not relax model revisions, dimensions, preprocessing or licenses to make the shared runtime fit.

## Acceptance checklist

- [ ] A repository-owned, digest-pinned shared GPU base is built once and inherited by all six model services; the derived images do not introduce another heavyweight CUDA/PyTorch base lineage.
- [ ] All six service lockfiles and runtime probes report the same Python 3.14 target and one matching `torch`/`torchaudio` pair, unless a documented reproducible incompatibility is explicitly accepted as a blocker rather than hidden.
- [ ] One exact Transformers version/source is installed in the shared base and is importable by every service without per-service reinstallation; Parakeet, BGE-M3, WeSpeaker and pyannote compatibility is tested.
- [ ] Model weights and model/package caches are external to image layers and mounted read-only at runtime where applicable.
- [ ] Layer inspection proves that the heavy base stack is shared once; every derived image's unique bytes and the BuildKit cache delta are recorded against the baseline. No per-service layer above 1 GiB is accepted without an explicit explanation in the evidence.
- [ ] All six real GPU smokes pass on the RTX 5090 with unchanged model revisions, dimensions, preprocessing and service contracts.
- [ ] A safe, targeted cleanup procedure and a disk-accounting runbook are documented; no broad prune is required for routine rebuilds.
- [ ] Required evidence below is linked and applies to the reviewed commit/configuration.
